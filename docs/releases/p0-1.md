# P0-1 — 발송 실패와 미리보기에서도 원가를 잃지 않기

기준: `0cdaf83`, 브랜치 `claude/ai-bot-automation-monetization-vimz44`.
사용자가 2026-09-22에 사전 감사/계획을 확인하고 구현 진행을 승인했다.

## CHANGELOG

- 기존 수집 → Claude → 사람에게 초안 발송 구조에 계측만 추가했다.
- LLM 결과는 본문과 입출력 usage를 담은 dataclass다. 잘림/거절 방어를 유지하고,
  빈 본문도 성공 발송으로 표시하지 않는다.
- `history.enabled/directory/pricing_file`을 고객 YAML에 노출했다.
- 실행 회차별 JSONL 장부, 모델별 공통 단가표, `botkit report --month YYYY-MM`을 추가했다.
- 생성 후 발송 실패, 일부 청크/싱크만 성공, dry-run 비용을 기록한다.
- 응답 유실 비용은 `null`/`unknown`이며 0원으로 위장하지 않는다.
- API 응답/입출력 원문·토큰·chat ID를 장부에 저장하지 않는다.
- Actions의 수동/dry-run/실패 실행에도 이력을 캐시/90일 요청 artifact로 보존한다.
- 수동 job 입력은 BOTKIT_JOB 값으로 전달하며 `.env.example`/Actions 양쪽에 선언했다.
- 시트 되쓰기 미구현, 시트 필터의 열 제거 불가를 판매 문서에 명확히 했다.
- 기존 예시 3개는 disabled 유지. 새 DB/서버/대시보드/패키지는 추가하지 않았다.

| 실서비스 실행 | 미실행. 실제 Claude/Telegram 수신 및 운영 Actions 이력 복원은 미검증 |

테스트에는 입력 정상/빈 입력/잘못된 설정, LLM 오류/timeout/usage 이상/거절/잘림,
Telegram 오류/부분 발송/429 재시도, 디스크 쓰기 실패, 월 경계, 백업 중복/충돌,
손상 장부, 미확인 비용 표시, Actions 저장 조건이 포함된다. 각 신규 테스트에 목적 docstring이 있다.

기존 테스트 변경 이유: P0-1이 문자열에서 dataclass 반환으로 계약을 바꾸므로 LLM
본문 assertion을 `.text`로 옮기고 usage assertion을 추가했다. runner mock도 구조화된
생성/발송 결과로 갱신했다. 기존 본문·발송·실패 격리·중복 방지 assertion은 제거하지 않았다.
runner 테스트의 장부는 tmp_path에 격리했다.

기존 autocpna/SQLAlchemy의 datetime.utcnow 경고 78개는 Python 3.12에서 그대로 남는다.
CI Python 3.11 결과는 해당 커밋의 GitHub Actions 실행 결과로 별도 확인한다.

Ruff의 최초 44개 오류는 0.16 기본 규칙 확대에서 발생했다. 기존 0.15 기본 규칙
`E4,E7,E9,F`를 명시하는 도구 설정만 별도 커밋했다. 근거는
[공식 0.16 마이그레이션 안내](https://astral.sh/blog/ruff-v0.16.0)다.
autocpna 소스나 기존 테스트를 일괄 수정해서 lint를 맞추지 않았다.

## DEPLOYMENT PLAN

1. 기능/테스트/문서를 P0-1 한 커밋으로 묶고 지정 작업 브랜치에만 푸시한다. PR은 만들지 않는다.
2. push로 동작하는 CI에서 Python 3.11의 Ruff/전체 테스트를 확인한다.
3. 운영 배포 전 사용자에게 이 기록과 CI 결과를 보고하고 승인받는다.
4. 승인된 비고객 데모 계정/가상 데이터로 validate → dry-run → 실제 수신을 검증한다.
   dry-run도 유료 API를 호출한다. 필요한 계정/키는 환경변수 또는 Secrets로 설정한다.
5. 별도 승인 후 운영 워크플로에서 수동/스케줄 경로를 실행하고 artifact 복원 및 report를 확인한다.

작업 브랜치 push는 운영 스케줄 활성화나 고객 연결 승인이 아니다.
Production 변경/고객 연결/데이터 migration/최종 납품/유료 API 활성화/크몽 게시를 자동 실행하지 않는다.

## KNOWN ISSUES

- 캐시/artifact는 영구 장부가 아니다. 누락 구간·만료 전 운영자 백업과 API 청구서 대조가 필요하다.
- 원가 추정은 일반 직접 Messages API 입출력 토큰만 대상으로 하며 SDK의 응답 없는 내부
  재시도, 캐시/도구/배치/지역 요금·세금·환율 등을 완전히 정산하지 않는다.
- 일부 발송 뒤 실패, 발송 뒤 장부 저장 실패는 재실행 시 중복될 수 있다. 상태 미기록 방어는 유지한다.
- 같은 장부에 대한 로컬 다중 프로세스 동시 실행은 지원하지 않는다. Actions는 직렬화한다.
- 장부에는 보고 본문이 없다. 과거 보고 재전달이나 승인 모드를 완성했다고 판매하면 안 된다.
- P0-2 시크릿 격리, P0-3 승인 전달, P1 기능은 이번 작업에 포함하지 않았다.
- 기존 source/API 오류의 CLI 원문 출력 경로까지 전면 정비한 것은 아니다.
  새 장부는 오류 단계/종류만 저장하고 Telegram 통신 오류는 토큰이 포함된 URL을 출력하지 않는다.
- 월 기준은 UTC 예정 회차이며 고객 현지 달력 월과 다를 수 있다.
- 자동 스케줄 재시도는 해당 회차가 tick 구간에 남아 있을 때만 가능하다.

## ROLLBACK PLAN

- 운영 변경 승인을 받은 경우에만 적용: 실행 중인 작업을 확인하고 새 실행을 잠시 중단한 뒤,
  상태 JSON과 월별 JSONL/artifact를 접근 제한된 위치에 백업한다.
- P0-1 기능 커밋을 `git revert <P0-1 커밋>`으로 되돌린다. Ruff 호환성 커밋은 별도이므로 유지 가능하다.
- 기존 state.json을 유지하고 이력 파일은 삭제하지 않는다. 롤백 전 장부의 별도 사본을 보관한다.
- 회귀 테스트와 예시 잡 설정을 확인한 후 승인된 스케줄을 재개한다.
- 캐시 삭제나 강제 reset으로 롤백하지 않는다. 일부 메시지가 이미 도착한 실행은 채널을 확인한 후 수동 판단한다.
